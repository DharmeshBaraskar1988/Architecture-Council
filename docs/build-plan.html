How the council reaches one agreed answer, and what we build first

Every stage (strategy, requirements, architecture) runs the same debate. Agents propose from facts, attack each other's proposals, get fact-checked, and vote. The result is one position with an agreement percentage. Unanimity isn't required; evidence and the vote decide, and the human reviewer has the last word. Options come from every verified source (Azure, AWS, GCP, SaaS vendors, open source, and what your company already owns), and only properly licensed, production-ready ones can be chosen for production. Phase 1 builds this loop end to end for the Strategy agent.

Roles

Agents and their work

Six agents, each with one job and a model from a different provider where it matters, so they don't share blind spots. A proposer and its challenger never run on the same provider. Four agents vote. The chair and the fact checker stay neutral.

Models are set in config/personas.yaml. Phase 1 can run on two providers. The Strategist is built in depth; the other panelists reuse the same agent runtime with their own persona prompts.

Decision rule

Voting and the agreement percentage

Agreement doesn't mean everyone said yes. It combines how the agents voted with how strong the surviving evidence is, so four agents repeating a weak argument can't outvote one verified fact.

Vote support V = Σ(confidence × stance) ÷ Σ confidence stance: adopt 1 · adopt with condition 0.5 · reject 0 Evidence E = W_for ÷ (W_for + W_against) W = Σ strength × relevance × verified Agreement A = 0.6 × V + 0.4 × E
Evidence sourceStrengthVerified factor
Org policy, confirmed compliance factBinding: skips the voteVerified 1 · Partly supports 0.5 · Unverified 0 · Contradicted: argument removed and flagged
PRD fact (confirmed, page cited)3
Decision database precedent3 × context match
Official standard or vendor docs3
Engineering case study2 × context match
Reasoning with no source0Shown, never counted
AgreementOutcomeWhat happens next
75–100%SelectedAdopted; goes to the reviewer for sign-off
60–74%Selected with conditionModerator writes the guardrail (a revisit trigger) from the strongest objection
40–59%Reviewer decidesOne compromise and re-vote; if still here, the reviewer chooses with both sides shown
0–39%RejectedRecorded with the reasons, so it isn't proposed again without new facts

Rules that override the percentage

  • Binding: org policy or a confirmed compliance fact (card payments → PCI DSS) means Selected at 100%. Agents vote only on how to apply it.
  • Assumed key fact: if the decision depends on an assumption, it's Parked and the question goes to the gray area.
  • Unanswered strong objection: caps the outcome at Reviewer decides, whatever the %.
  • Untested consensus: if nobody challenged, the Critic must argue the opposite before the vote closes.
  • Human override: the reviewer can change any outcome. The reason is recorded next to the agents' %.

Thresholds and the 0.6 / 0.4 split live in config/consensus.yaml. We tune them on golden sessions in Phase 1.

Trust

Fact check: what's checked, what isn't, known issues

The fact checker is mostly code. An LLM judge is used only for one question: does this source actually support this claim? Everything not checked is labelled on screen, so nobody mistakes an opinion for a fact.

Checked

  • PRD quotes: exact text match on the cited page
  • Citations: URL was retrieved by us; quote found in the stored page; fetch date recorded
  • Support: LLM judge rates supports, partly, or contradicts
  • Recency: flags pages older than the catalog's limit or marked deprecated
  • Precedents: context match % (scale, team, domain, cloud)
  • Applicability: framework rule fired on a real fact
  • Numbers: scores, % and costs recomputed by code, never by an LLM
  • Production gate: licence (SPDX id vs our licence policy), GA vs preview, published SLA, maintenance activity, data-use terms, region availability

Not checked, labelled

  • Judgments ("this is simpler"): labelled Judgment, weight 0 unless backed
  • Forecasts (future traffic, growth): labelled Assumption, sent to gray area
  • Whether a case study generalises: only context match is shown
  • Vendor claims beyond official docs: not used as evidence
  • Negotiated prices or discounts: list prices only, marked Estimate
  • Team skill claims: taken from the PRD or reviewer, not verified

Known issues and fixes

  • Misquoting: exact-match check; failed match becomes Unverified
  • Invented URLs: only URLs returned by our retriever are accepted
  • Paywalled or blocked pages: Unverified, never strong
  • Conflicting sources: both shown; official and newer ranks higher
  • Agents converging too fast: blind proposals, blind votes, mandatory counter-case
  • Instructions hidden in crawled pages: treated as data, stripped before prompts
  • Ambiguous PRD: fact marked Assumed, decision Parked
  • Licence or terms change after selection: catalog re-verified monthly; affected decisions flagged for review
  • Model weights with use limits: the model licence is checked separately from the code licence

Steps we follow every day

  1. Build in thin slices. Each day ends with something that runs on a real sample PRD.
  2. Run the golden samples on every change. Prompts live in git; a prompt change that moves an outcome must be explained.
  3. Code decides numbers. Percentages, weights and gate results come from tested functions, never from a model.
  4. Weekly demo with a gate. We don't start the next week's work until that week's demo works.
  5. Cost cap. Set a spending limit per provider for Phase 1 and check Langfuse daily.
  6. Our own tools pass our own gate. Every library in the stack above has a licence that allows commercial use.
